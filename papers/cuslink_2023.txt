<div id="abstract1" class="ltx_abstract"><h6 class="ltx_title ltx_title_abstract">Abstract</h6>
    
<p id="abstract1.1" class="ltx_p">In this paper, we propose cuSLINK, a novel and state-of-the-art reformulation of the SLINK algorithm on the GPU which requires only <math id="abstract1.m1" class="ltx_Math" alttext="O(Nk)" display="inline" intent=":literal"><semantics><mrow><mi>O</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><mi>N</mi><mo lspace="0em" rspace="0em">​</mo><mi>k</mi></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">O(Nk)</annotation></semantics></math> space and uses a parameter <math id="abstract1.m2" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math> to trade off space and time. We also propose a set of novel and reusable building blocks that compose cuSLINK. These building blocks include highly optimized computational patterns for <math id="abstract1.m3" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN graph construction, spanning trees, and dendrogram cluster extraction. We show how we used our primitives to implement cuSLINK end-to-end on the GPU, further enabling a wide range of real-world data mining and machine learning applications that were once intractable. In addition to being a primary computational bottleneck in the popular HDBSCAN algorithm, the impact of our end-to-end cuSLINK algorithm spans a large range of important applications, including cluster analysis in social and computer networks, natural language processing, and computer vision. Users can obtain cuSLINK at <a target="_blank" href="https://docs.rapids.ai/api/cuml/latest/api/#agglomerative-clustering" title="" class="ltx_ref ltx_url ltx_font_typewriter">https://docs.rapids.ai/api/cuml/latest/api/#agglomerative-clustering</a></p>
  
</div>

<section id="S1" class="ltx_section">
<h2 class="ltx_title ltx_title_section"><span class="ltx_tag ltx_tag_section">1 </span>Introduction</h2>

<div id="S1.p1" class="ltx_para">
<p id="S1.p1.1" class="ltx_p">Hierarchical agglomerative clustering (HAC) is an important and fundamental algorithm for classical machine learning and data mining. HAC variants are used in many different informatics disciplines such as micro array analysis, genome clustering, computer vision, document clustering, and social network analysis <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib24" title="" class="ltx_ref">24</a>]</cite>. In particular, the Single-Link HAC is still critically important in bioinformatics and genomics<cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib31" title="" class="ltx_ref">31</a>, <a href="#bib.bib1" title="" class="ltx_ref">1</a>, <a href="#bib.bib11" title="" class="ltx_ref">11</a>]</cite>, but a challenge to use due to its <math id="S1.p1.m1" class="ltx_Math" alttext="\mathcal{O}(N^{2})" display="inline" intent=":literal"><semantics><mrow><mi class="ltx_font_mathcaligraphic">𝒪</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><msup><mi>N</mi><mn>2</mn></msup><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">\mathcal{O}(N^{2})</annotation></semantics></math> cost where <math id="S1.p1.m2" class="ltx_Math" alttext="N" display="inline" intent=":literal"><semantics><mi>N</mi><annotation encoding="application/x-tex">N</annotation></semantics></math> is the number of items to be clustered. Hierarchical agglomerative clustering builds up a hierarchy of clusters from a set of vectors bottom-up, by starting with each vector in its own cluster and merging pairs of vectors together based on predefined similarity criteria until a common root is reached, which produces this quadratic lower bound.</p>
</div>
<div id="S1.p2" class="ltx_para">
<p id="S1.p2.1" class="ltx_p">The seminal SLINK algorithm <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib27" title="" class="ltx_ref">27</a>]</cite> provided the first <math id="S1.p2.m1" class="ltx_Math" alttext="\mathcal{O}(N^{2})" display="inline" intent=":literal"><semantics><mrow><mi class="ltx_font_mathcaligraphic">𝒪</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><msup><mi>N</mi><mn>2</mn></msup><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">\mathcal{O}(N^{2})</annotation></semantics></math> time and <math id="S1.p2.m2" class="ltx_Math" alttext="\mathcal{O}(N)" display="inline" intent=":literal"><semantics><mrow><mi class="ltx_font_mathcaligraphic">𝒪</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mi>N</mi><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">\mathcal{O}(N)</annotation></semantics></math> space algorithm for the Single-link HAC problem. However, it has evaded efficient parallel implementation due to a lack of bulk work in the SLINK algorithm, causing communication overhead to dominate runtime. In this work, we will instead use a Minimum Spanning Tree (MST) based approach to the Single-link HAC that allows us to perform more parallel work, but at a potentially larger compute and memory complexity of <math id="S1.p2.m3" class="ltx_Math" alttext="\mathcal{O}(N^{2}+Nk\log N)" display="inline" intent=":literal"><semantics><mrow><mi class="ltx_font_mathcaligraphic">𝒪</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><msup><mi>N</mi><mn>2</mn></msup><mo>+</mo><mrow><mi>N</mi><mo lspace="0em" rspace="0em">​</mo><mi>k</mi><mo lspace="0.167em" rspace="0em">​</mo><mrow><mi>log</mi><mo lspace="0.167em">⁡</mo><mi>N</mi></mrow></mrow></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">\mathcal{O}(N^{2}+Nk\log N)</annotation></semantics></math> and <math id="S1.p2.m4" class="ltx_Math" alttext="\mathcal{O}(Nk)" display="inline" intent=":literal"><semantics><mrow><mi class="ltx_font_mathcaligraphic">𝒪</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><mi>N</mi><mo lspace="0em" rspace="0em">​</mo><mi>k</mi></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">\mathcal{O}(Nk)</annotation></semantics></math> respectively. This required inventing a new parallel MST approach that efficiently performs the distance computations by an iterative expansion of a <math id="S1.p2.m5" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-nearest neighbor graph. We find in practice, this trade-off is worth it by enabling a GPU implementation capable of 2290<math id="S1.p2.m6" class="ltx_Math" alttext="\times" display="inline" intent=":literal"><semantics><mo>×</mo><annotation encoding="application/x-tex">\times</annotation></semantics></math> faster runtime over common CPU implementations, and in all our tests is faster than alternative options today. An added benefit of this primitives-based approach is the ability to generalize cuSLINK for other distance measures, even in non-metric spaces.</p>
</div>
<div id="S1.p3" class="ltx_para">
<p id="S1.p3.1" class="ltx_p">We term our approach and implementation cuSLINK for its use of CUDA APIs and it produces an exact solution to the SLHC problem. The primitives we used to build cuSLINK are modular and can be reused to compose other important algorithms for graph and machine learning. For this reason, we provide separate benchmarks for these primitives, in addition to end-to-end benchmarks of our cuSLINK implementation against the currently available state-of-the-art. cuSLINK and its primitives are fully open source and have been contributed upstream to the RAFT library (https://github.com/rapidsai/raft).</p>
</div>
<div id="S1.p4" class="ltx_para">
<p id="S1.p4.1" class="ltx_p">In the following <a href="#S2" title="2 Related Work ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 2</span></a>, we will outline related works and better shape the motivation for both our modular design and contributions. We present our contribution in <a href="#S3" title="3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 3</span></a>, and detail our primitives, as well as our novel reformulation of single-linkage hierarchical clustering for the GPU. These primitives include constructing knn graphs by fusing the k-selection operation with the computation of distances, computing an MST using a variant of Borůvka’s classic parallel algorithm, and a novel method for extracting flattened clusters from a dendrogram. <a href="#S4" title="4 Experiments ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 4</span></a> compares the performance of our single-linkage hierarchical clustering algorithm, as well as its building blocks, against previous works.</p>
</div>
</section>
<section id="S2" class="ltx_section">
<h2 class="ltx_title ltx_title_section"><span class="ltx_tag ltx_tag_section">2 </span>Related Work</h2>

<div id="S2.p1" class="ltx_para">
<p id="S2.p1.1" class="ltx_p">Single-linkage hierarchical clustering is commonly referred to as ’nearest neighbors’ clustering and as such, our implementation makes direct use of nearest neighbors computations in order to shrink the memory footprint of the naive computation of single-linkage clustering and providing a GPU-accelerated version that borrows its foundation from the original SLINK <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib27" title="" class="ltx_ref">27</a>]</cite>.</p>
</div>
<div id="S2.p2" class="ltx_para">
<p id="S2.p2.1" class="ltx_p">The original SLINK algorithm maintains 3 arrays, each of size <math id="S2.p2.m1" class="ltx_Math" alttext="n" display="inline" intent=":literal"><semantics><mi>n</mi><annotation encoding="application/x-tex">n</annotation></semantics></math> and loops over the range <math id="S2.p2.m2" class="ltx_Math" alttext="[1,n]" display="inline" intent=":literal"><semantics><mrow><mo stretchy="false">[</mo><mn>1</mn><mo>,</mo><mi>n</mi><mo stretchy="false">]</mo></mrow><annotation encoding="application/x-tex">[1,n]</annotation></semantics></math>, building up the dendrogram level by level, using two arrays of pointers to represent the dendrogram itself and a third to store distances. Sibsen notes that <math id="S2.p2.m3" class="ltx_Math" alttext="O(n^{2})" display="inline" intent=":literal"><semantics><mrow><mi>O</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><msup><mi>n</mi><mn>2</mn></msup><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">O(n^{2})</annotation></semantics></math> is the optimally efficient runtime upper bound because each neighbor pair will ultimately need to be compared at least once. The challenge with this algorithm, however, is in SLINK’s equivalence to the inherently iterative nature of Prim’s algorithm for constructing an MST. Our algorithm performs a similar iterative step to perform the agglomerative labeling, but we perform this step on the sorted edges of an MST, after all needed distances have been computed. As we describe below, we use a novel variant of Borůvka’s algorithm to construct the MST in parallel. In <a href="#S3" title="3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 3</span></a>, we note that our formulation incresases the overall complexity to <math id="S2.p2.m4" class="ltx_Math" alttext="O(N^{2}+Nk\log N)" display="inline" intent=":literal"><semantics><mrow><mi>O</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><msup><mi>N</mi><mn>2</mn></msup><mo>+</mo><mrow><mi>N</mi><mo lspace="0em" rspace="0em">​</mo><mi>k</mi><mo lspace="0.167em" rspace="0em">​</mo><mrow><mi>log</mi><mo lspace="0.167em">⁡</mo><mi>N</mi></mrow></mrow></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">O(N^{2}+Nk\log N)</annotation></semantics></math> but enables a high amount of parallelism.</p>
</div>
<div id="S2.p3" class="ltx_para">
<p id="S2.p3.1" class="ltx_p">Several approaches exist to perform single-linkage hierarchical clustering in parallel architectures <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib20" title="" class="ltx_ref">20</a>]</cite>. Many are variants of Borůvka and often combine the affinities graph construction with the MST by computing distance metrics right in the solver <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib3" title="" class="ltx_ref">3</a>, <a href="#bib.bib22" title="" class="ltx_ref">22</a>]</cite>. Other approaches build upon Kruskal’s algorithm, either by exploiting parallelism within different steps, such as the sorting step, or by building many trees independently in parallel and merging them into a single hierarchy <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib13" title="" class="ltx_ref">13</a>, <a href="#bib.bib14" title="" class="ltx_ref">14</a>]</cite>. The latter approach forms the basis for an end-to-end parallel algorithm for single-linkage hierarchical clustering, even up to the dendrogram construction, but at the cost of performing many redundant computations and duplicating memory. While there have been claims that only the pairwise distance computations can benefit from GPU-acceleration <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib7" title="" class="ltx_ref">7</a>]</cite>, we demonstrate in <a href="#S4" title="4 Experiments ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 4</span></a> that the linkage and cluster extraction steps also find performance gains.</p>
</div>
<div id="S2.p4" class="ltx_para">
<p id="S2.p4.1" class="ltx_p">The FAISS library is well known for containing state-of-the-art implementations of both exact and approximate nearest neighbors search on the GPU <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib16" title="" class="ltx_ref">16</a>]</cite>, though their exact implementation of nearest neighbors, known as brute-force, computes and stores an intermediate buffer of pairwise distances, performing a k-selection on each buffer. As we highlight in <a href="#S3" title="3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 3</span></a>, we improve upon this design by fusing the computation of the distances with the k-selection when <math id="S2.p4.m1" class="ltx_Math" alttext="k\leq 64" display="inline" intent=":literal"><semantics><mrow><mi>k</mi><mo>≤</mo><mn>64</mn></mrow><annotation encoding="application/x-tex">k\leq 64</annotation></semantics></math>, allowing us to lower the memory footprint while also reducing the number of reads and writes to global memory.</p>
</div>
<div id="S2.p5" class="ltx_para">
<p id="S2.p5.1" class="ltx_p">Fast <math id="S2.p5.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN computations are critical for many types of algorithms in a class we refer to as ’neighborhood methods’ which include information retrieval, clustering, dimensionality reduction, and classification/regression. Centroid-based clustering algorithms such as <math id="S2.p5.m2" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-means and <math id="S2.p5.m3" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-medioids rely on a fast computation of <math id="S2.p5.m4" class="ltx_Math" alttext="1" display="inline" intent=":literal"><semantics><mn>1</mn><annotation encoding="application/x-tex">1</annotation></semantics></math>-nearest neighbors, or closest centroid, to each training data point. Manifold learning algorithms such as TSNE <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib6" title="" class="ltx_ref">6</a>]</cite> and UMAP <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib19" title="" class="ltx_ref">19</a>]</cite> rely on a special class of worse-case <math id="S2.p5.m5" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN computations known as all-neighbors problems <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib8" title="" class="ltx_ref">8</a>, <a href="#bib.bib23" title="" class="ltx_ref">23</a>]</cite> to construct a graph of affinities. Similar to single-linkage clustering, the HDBSCAN algorithm, which can be formulated as a special case of single-linkage clustering, these problems specifically require a fast <math id="S2.p5.m6" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN as all <math id="S2.p5.m7" class="ltx_Math" alttext="n^{2}" display="inline" intent=":literal"><semantics><msup><mi>n</mi><mn>2</mn></msup><annotation encoding="application/x-tex">n^{2}</annotation></semantics></math> point pairs (or <math id="S2.p5.m8" class="ltx_Math" alttext="\frac{n}{2}" display="inline" intent=":literal"><semantics><mfrac><mi>n</mi><mn>2</mn></mfrac><annotation encoding="application/x-tex">\frac{n}{2}</annotation></semantics></math> in metric spaces <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib26" title="" class="ltx_ref">26</a>]</cite>) might need to be computed in the worst case for exact results.</p>
</div>
<div id="S2.p6" class="ltx_para">
<p id="S2.p6.1" class="ltx_p">A natural optimization for <math id="S2.p6.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN-based approaches is to reduce computations by shrinking dimensionality <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib21" title="" class="ltx_ref">21</a>]</cite>, partitioning <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib25" title="" class="ltx_ref">25</a>, <a href="#bib.bib10" title="" class="ltx_ref">10</a>, <a href="#bib.bib5" title="" class="ltx_ref">5</a>]</cite> and/or quantizing <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib15" title="" class="ltx_ref">15</a>]</cite> the space. Such methods can offer further speedups, sometimes at the expense of correctness. cuSLINK demonstrates state-of-the-art performance, but the primitives-based approach also leaves room for more optimized <math id="S2.p6.m2" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN algorithms to be used.</p>
</div>
<div id="S2.p7" class="ltx_para">
<p id="S2.p7.1" class="ltx_p">Implementation of the Borůvka algorithm on the GPU has been considered before by several authors <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib9" title="" class="ltx_ref">9</a>, <a href="#bib.bib30" title="" class="ltx_ref">30</a>, <a href="#bib.bib2" title="" class="ltx_ref">2</a>]</cite>. Early attempts demonstrated speedups in comparison to parallel CPU solutions but focused on optimizing specific sparsity patterns <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib9" title="" class="ltx_ref">9</a>]</cite> or data structures <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib12" title="" class="ltx_ref">12</a>]</cite>. Those results worked for the initial goal, but tended to break down as the scope changed <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib2" title="" class="ltx_ref">2</a>]</cite>. The breadth of MST applications kept growing meanwhile <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib17" title="" class="ltx_ref">17</a>]</cite>, and translated to many distribution patterns and use cases. Designing a fast parallel solution resilient to multiple graph types and properties remains a primary concern.</p>
</div>
<div id="S2.p8" class="ltx_para">
<p id="S2.p8.1" class="ltx_p">Recent shifts in human communication, such as mobile phones and the internet of things (IoT), coupled with technical progress, has triggered an extensive growth of data volume. Scalability and speed have become a major concern for MST solvers. Previous solutions tended to primarily focus on performance, often at the cost of generous memory allocations. One of the strengths of the GPU architecture is the memory bandwidth, but the memory size is limited. We designed our MST algorithm to be memory efficient by avoiding explicit graph coarsening in order to scale further than previous implementations: past a billion edges on a single GPU.</p>
</div>
<div id="S2.p9" class="ltx_para">
<p id="S2.p9.1" class="ltx_p">A common problem in previous variants is cycle formation. Multiple edges of equal minimum weight between two components lead to multiple equivalent solutions. This results in ties when considering parallel execution, and can be a source of non-deterministic outputs. Weight alterations have been successfully applied to algebraic multi-grid aggregation in the past as a way to extract parallelism and break ties between strongly coupled nodes <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib18" title="" class="ltx_ref">18</a>]</cite>. Unfortunately, random weight alterations cannot be applied directly without risking a change in the global relative ordering of the weights and thus the MST solution. In this paper, we propose an alteration that guarantees that all weights are different while preserving their relative order.</p>
</div>
<div id="S2.p10" class="ltx_para">
<p id="S2.p10.1" class="ltx_p">Our implementation adopts the <span id="S2.p10.1.1" class="ltx_text ltx_font_italic">scipy.hierarchy.linkage</span> format, which is also used by Scikit-learn, making it directly available on a trained <span id="S2.p10.1.2" class="ltx_text ltx_font_italic">AgglomerativeClustering</span> estimator. In addition to enabling SLINK, our MST implementation is also capable of constructing a maximum spanning tree, which enables our hierarchical clustering algorithm to also compute a complete-linkage clustering.</p>
</div>
</section>

<p id="S3.p2.1" class="ltx_p">We start by converting tabular inputs from <math id="S3.p2.m1" class="ltx_Math" alttext="N" display="inline" intent=":literal"><semantics><mi>N</mi><annotation encoding="application/x-tex">N</annotation></semantics></math> points in <math id="S3.p2.m2" class="ltx_Math" alttext="d" display="inline" intent=":literal"><semantics><mi>d</mi><annotation encoding="application/x-tex">d</annotation></semantics></math> dimensions into a sparse <math id="S3.p2.m3" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN graph of affinities, which is then used as input to compute the MST. As mentioned, the original SLINK algorithm computes the MST sequentially by computing and maintaining the <math id="S3.p2.m4" class="ltx_Math" alttext="1" display="inline" intent=":literal"><semantics><mn>1</mn><annotation encoding="application/x-tex">1</annotation></semantics></math>-NN of the data points (and clusters) while constructing each of the O(<math id="S3.p2.m5" class="ltx_Math" alttext="\log N" display="inline" intent=":literal"><semantics><mrow><mi>log</mi><mo lspace="0.167em">⁡</mo><mi>N</mi></mrow><annotation encoding="application/x-tex">\log N</annotation></semantics></math>) levels of the resulting dendrogram. Our cuSLINK breaks the algorithm into four steps: 1) construction of affinities graph, 2) construction of MST, 3) construction of the dendrogram, and 4) extraction of flat cluster assignments from the dendrogram. This separation uses Amdahl’s Law to allow parallelism of the most performance-critical pieces and isolates the sequential bits to only the third step.</p>
</div>
<div id="S3.p3" class="ltx_para">
<p id="S3.p3.1" class="ltx_p">In order for an MST to converge, the edges that it has available as input need to form a connected graph and it is not guaranteed that the closest <math id="S3.p3.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math> neighbors to each data point will form a connected graph. In the case where the MST construction doesn’t converge, resulting in a minimium spanning forest (MSF, i.e., multiple MSTs that are not connected), we compute an additional <math id="S3.p3.m2" class="ltx_Math" alttext="1" display="inline" intent=":literal"><semantics><mn>1</mn><annotation encoding="application/x-tex">1</annotation></semantics></math>-NN across the resulting super-vertexes in the MSF and perform another iteration of the MST with the new edges to connect the super vertices. It’s possible there could be multiple iterations of computing <math id="S3.p3.m3" class="ltx_Math" alttext="1" display="inline" intent=":literal"><semantics><mn>1</mn><annotation encoding="application/x-tex">1</annotation></semantics></math>-NNs until the MSF converges to an MST, the number of iterations bounded from above by O(<math id="S3.p3.m4" class="ltx_Math" alttext="\log N" display="inline" intent=":literal"><semantics><mrow><mi>log</mi><mo lspace="0.167em">⁡</mo><mi>N</mi></mrow><annotation encoding="application/x-tex">\log N</annotation></semantics></math>) in the worst case when <math id="S3.p3.m5" class="ltx_Math" alttext="k=1" display="inline" intent=":literal"><semantics><mrow><mi>k</mi><mo>=</mo><mn>1</mn></mrow><annotation encoding="application/x-tex">k=1</annotation></semantics></math>. The algorithm for connecting anotherwise disconnected <math id="S3.p3.m6" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN graph is outlined in Algorithm <a href="#alg2" title="Algorithm 2 ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">2</span></a></p>

<div id="S3.p4" class="ltx_para">
<p id="S3.p4.1" class="ltx_p">The <math id="S3.p4.m1" class="ltx_Math" alttext="O(E\log V)" display="inline" intent=":literal"><semantics><mrow><mi>O</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><mi>E</mi><mo lspace="0.167em" rspace="0em">​</mo><mrow><mi>log</mi><mo lspace="0.167em">⁡</mo><mi>V</mi></mrow></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">O(E\log V)</annotation></semantics></math> complexity of computing the MST itself becomes <math id="S3.p4.m2" class="ltx_Math" alttext="O(Nk\log N)" display="inline" intent=":literal"><semantics><mrow><mi>O</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><mi>N</mi><mo lspace="0em" rspace="0em">​</mo><mi>k</mi><mo lspace="0.167em" rspace="0em">​</mo><mrow><mi>log</mi><mo lspace="0.167em">⁡</mo><mi>N</mi></mrow></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">O(Nk\log N)</annotation></semantics></math> in our formulation, since <math id="S3.p4.m3" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN bounds the number of edges, <math id="S3.p4.m4" class="ltx_Math" alttext="E" display="inline" intent=":literal"><semantics><mi>E</mi><annotation encoding="application/x-tex">E</annotation></semantics></math>, to <math id="S3.p4.m5" class="ltx_Math" alttext="N\times k" display="inline" intent=":literal"><semantics><mrow><mi>N</mi><mo lspace="0.222em" rspace="0.222em">×</mo><mi>k</mi></mrow><annotation encoding="application/x-tex">N\times k</annotation></semantics></math> and <math id="S3.p4.m6" class="ltx_Math" alttext="V=N" display="inline" intent=":literal"><semantics><mrow><mi>V</mi><mo>=</mo><mi>N</mi></mrow><annotation encoding="application/x-tex">V=N</annotation></semantics></math>. Our implementation uses brute-force <math id="S3.p4.m7" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN, so we still perform <math id="S3.p4.m8" class="ltx_Math" alttext="N^{2}" display="inline" intent=":literal"><semantics><msup><mi>N</mi><mn>2</mn></msup><annotation encoding="application/x-tex">N^{2}</annotation></semantics></math> distance computations, resulting in <math id="S3.p4.m9" class="ltx_Math" alttext="O(N^{2}+Nk\log N)" display="inline" intent=":literal"><semantics><mrow><mi>O</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><msup><mi>N</mi><mn>2</mn></msup><mo>+</mo><mrow><mi>N</mi><mo lspace="0em" rspace="0em">​</mo><mi>k</mi><mo lspace="0.167em" rspace="0em">​</mo><mrow><mi>log</mi><mo lspace="0.167em">⁡</mo><mi>N</mi></mrow></mrow></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">O(N^{2}+Nk\log N)</annotation></semantics></math> overall commputational complexity. While this complexity is slightly worse than the SLINK algorithm, it does so because it allows more parallel computation to occur with less overhead, resulting in a lower total runtime.</p>
</div>
<div id="S3.p5" class="ltx_para">
<p id="S3.p5.1" class="ltx_p">As we describe in Section <a href="#S3.SS3.SSS2" title="3.3.2 Cut the Dendrogram ‣ 3.3 Dendrogram ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 3.3.2</span></a>, flattened cluster assignments are obtained for each point <math id="S3.p5.m1" class="ltx_Math" alttext="n\in N" display="inline" intent=":literal"><semantics><mrow><mi>n</mi><mo>∈</mo><mi>N</mi></mrow><annotation encoding="application/x-tex">n\in N</annotation></semantics></math> by cutting the dendrogram at the level which yields the desired number of clusters ands assigning a unique label to each resulting connected component. While not currently supported by cuSLINK, complete-linkage clustering can be obtained by computing the maximum spanning tree and sorting the resulting edges in descending order. With our building blocks, it’s also possible to implement a variant which accepts a distance threshold for which to cut the dendrogram, however we leave this to future work.</p>
</div>
<div id="S3.p6" class="ltx_para">
<p id="S3.p6.1" class="ltx_p">Unlike the original SLINK formulation, cuSLINK separates the construction of the dendrogram from the <math id="S3.p6.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN graph and MST steps in order to maximize parallelism of the former steps since the order of dendrogram construction is important, making it inherently sequential. Algorithm <a href="#alg1" title="Algorithm 1 ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref"><span class="ltx_text ltx_ref_tag">1</span></a> shows the cuSLINK steps and Algorithm <a href="#alg2" title="Algorithm 2 ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref"><span class="ltx_text ltx_ref_tag">2</span></a> shows the steps to finding additional edges for connecting the super-vertices.</p>
</div>
<section id="S3.SS1" class="ltx_subsection">
<h3 class="ltx_title ltx_title_subsection"><span class="ltx_tag ltx_tag_subsection">3.1 </span>Nearest Neighbors</h3>

<section id="S3.SS1.SSS1" class="ltx_subsubsection">
<h4 class="ltx_title ltx_title_subsubsection"><span class="ltx_tag ltx_tag_subsubsection">3.1.1 </span><math id="S3.SS1.SSS1.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN Graph Construction</h4>

<div id="S3.SS1.SSS1.p1" class="ltx_para">
<p id="S3.SS1.SSS1.p1.1" class="ltx_p">The connectivities graph is constructed in parallel using a novel GPU-accelerated brute-force <math id="S3.SS1.SSS1.p1.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN primitive that, as we will outline below, is able to fuse the k-selection steps with computation of the distances in order to lower the required memory footprint and remove the need for additional steps downstream.</p>
</div>
<div id="S3.SS1.SSS1.p2" class="ltx_para">
<p id="S3.SS1.SSS1.p2.1" class="ltx_p">A common approach to computing a brute-force <math id="S3.SS1.SSS1.p2.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN is to first break up the computation of the full <math id="S3.SS1.SSS1.p2.m2" class="ltx_Math" alttext="m\times n" display="inline" intent=":literal"><semantics><mrow><mi>m</mi><mo lspace="0.222em" rspace="0.222em">×</mo><mi>n</mi></mrow><annotation encoding="application/x-tex">m\times n</annotation></semantics></math> pairwise distance matrix into smaller tiles, each requiring an intermediate buffer of device memory. A k-selection is performed as a follow-on computation over each tile of pairwise distances to reduce the columns down to the <math id="S3.SS1.SSS1.p2.m3" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math> smallest (or largest) distances and output them to another memory buffer. If tiling over both dimensions of the pairwise distance matrix, additional k-selection steps might be needed. These intermediate tiles and k-selection steps require additional memory accesses that can be avoided when <math id="S3.SS1.SSS1.p2.m4" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math> is small enough such that the closest neighbors can be reduced into shared memory from each warp and selected within each thread-block. We use this novel insight to develop a fast <math id="S3.SS1.SSS1.p2.m5" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN strategy outlined in Alg. <a href="#alg3" title="Algorithm 3 ‣ 3.1.1

Our improved version is detailed in Alg. <a href="#alg10" title="Algorithm 10 ‣ Appendix Appendix A TopK Epilog Operations ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">10</span></a> in <a href="#Pt0.A1" title="Appendix Appendix A TopK Epilog Operations ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">Appendix Appendix A</span></a>. This step imposes a lot of pressure on the registers as each warp maintains its own thread-level queue of new values to be merged along with a warp-wide queue of the fully sorted top-k values and a register to store the current largest value in the warp-wide queue for early filtering of candidates. When the thread-level queues reach their max for new potential top-k values, a sorting and merging step is initiated synchronously in the warp by performing a bitonic sort of the thread-level values with the warp-level queue, reducing the warp-level queue back down to size <math id="S3.SS1.SSS1.p3.m2" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>. Our warp-level k-selection routine follows the same general design used in FAISS, but reduces the number of warp-selection computations, which require expensive synchronization between threads within each warp, using the stream compaction technique <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib4" title="" class="ltx_ref">4</a>]</cite> within each block.</p>

<div id="S3.SS1.SSS1.p4" class="ltx_para">
<p id="S3.SS1.SSS1.p4.1" class="ltx_p">At the block level, each warp performs its warp-level k-selection and stores the resulting <math id="S3.SS1.SSS1.p4.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math> selected distances and indices in shared memory. Next, in a grid-stride, each thread discards all distances and indices which are less than the previous warp-level k-selection, performing the stream compaction to write the new set of filtered indices and distances to shared memory. A warp-level <span id="S3.SS1.SSS1.p4.1.1" class="ltx_text ltx_font_italic">ballot_sync()</span> is performed over the filtered counts, <math id="S3.SS1.SSS1.p4.m2" class="ltx_Math" alttext="2\times 256" display="inline" intent=":literal"><semantics><mrow><mn>2</mn><mo lspace="0.222em" rspace="0.222em">×</mo><mn>256</mn></mrow><annotation encoding="application/x-tex">2\times 256</annotation></semantics></math> per warp and <math id="S3.SS1.SSS1.p4.m3" class="ltx_Math" alttext="2\times 8" display="inline" intent=":literal"><semantics><mrow><mn>2</mn><mo lspace="0.222em" rspace="0.222em">×</mo><mn>8</mn></mrow><annotation encoding="application/x-tex">2\times 8</annotation></semantics></math> per thread, resorting to a scan only if the number of filtered counts is <math id="S3.SS1.SSS1.p4.m4" class="ltx_Math" alttext="&gt;0" display="inline" intent=":literal"><semantics><mrow><mphantom></mphantom><mo>&gt;</mo><mn>0</mn></mrow><annotation encoding="application/x-tex">&gt;0</annotation></semantics></math>. For each set of <math id="S3.SS1.SSS1.p4.m5" class="ltx_Math" alttext="2\times 256" display="inline" intent=":literal"><semantics><mrow><mn>2</mn><mo lspace="0.222em" rspace="0.222em">×</mo><mn>256</mn></mrow><annotation encoding="application/x-tex">2\times 256</annotation></semantics></math> distances computed by a warp, the warp-select calls <span id="S3.SS1.SSS1.p4.1.2" class="ltx_text ltx_font_italic">any_sync()</span> a total of 128 times per grid-stride by whole thread block. With stream compaction, <span id="S3.SS1.SSS1.p4.1.3" class="ltx_text ltx_font_italic">ballot_sync()</span> needs to be called only 16 times in the best case.</p>
</div>

<h4 class="ltx_title ltx_title_subsubsection"><span class="ltx_tag ltx_tag_subsubsection">3.1.2 </span><math id="S3.SS1.SSS2.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN Graph Connection</h4>

<div id="S3.SS1.SSS2.p1" class="ltx_para">
<p id="S3.SS1.SSS2.p1.1" class="ltx_p">Unfortunately, a <math id="S3.SS1.SSS2.p1.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN alone with only a naive choice of <math id="S3.SS1.SSS2.p1.m2" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math> doesn’t often scale to larger datasets in practice as the size of <math id="S3.SS1.SSS2.p1.m3" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math> needed for the MST to converge to a single supervertex can grow significantly large, being bounded above by <math id="S3.SS1.SSS2.p1.m4" class="ltx_Math" alttext="k=N" display="inline" intent=":literal"><semantics><mrow><mi>k</mi><mo>=</mo><mi>N</mi></mrow><annotation encoding="application/x-tex">k=N</annotation></semantics></math> in the worst-case. Since our MST implementation is robust to this type of input, a minimum spanning forest (MSF) will be returned when this occurs and additional edges are added to the MSF by performing a <math id="S3.SS1.SSS2.p1.m5" class="ltx_Math" alttext="1" display="inline" intent=":literal"><semantics><mn>1</mn><annotation encoding="application/x-tex">1</annotation></semantics></math>-NN query that connects points only across different supervertices, or components, together before re-computing the MST.</p>

<section id="S3.SS2" class="ltx_subsection">
<h3 class="ltx_title ltx_title_subsection"><span class="ltx_tag ltx_tag_subsection">3.2 </span>Spanning Trees</h3>

<div id="S3.SS2.p1" class="ltx_para">
<p id="S3.SS2.p1.1" class="ltx_p">Since the graph is assumed to be undirected (<math id="S3.SS2.p1.m1" class="ltx_Math" alttext="w_{i,j}=w_{j,i}" display="inline" intent=":literal"><semantics><mrow><msub><mi>w</mi><mrow><mi>i</mi><mo>,</mo><mi>j</mi></mrow></msub><mo>=</mo><msub><mi>w</mi><mrow><mi>j</mi><mo>,</mo><mi>i</mi></mrow></msub></mrow><annotation encoding="application/x-tex">w_{i,j}=w_{j,i}</annotation></semantics></math>), the resulting adjacency matrix is symmetric. Our algorithm is resilient to negative weights and can solve the maximum spanning tree problem natively. The maximum spanning tree has weights greater than or equal to the weight of every other spanning tree, and is found by forming the additive inverse <math id="S3.SS2.p1.m2" class="ltx_Math" alttext="G^{\prime}=(V,-E)" display="inline" intent=":literal"><semantics><mrow><msup><mi>G</mi><mo>′</mo></msup><mo>=</mo><mrow><mo stretchy="false">(</mo><mi>V</mi><mo rspace="0em">,</mo><mrow><mo lspace="0em">−</mo><mi>E</mi></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">G^{\prime}=(V,-E)</annotation></semantics></math> and solving the MST problem on <math id="S3.SS2.p1.m3" class="ltx_Math" alttext="G^{\prime}" display="inline" intent=":literal"><semantics><msup><mi>G</mi><mo>′</mo></msup><annotation encoding="application/x-tex">G^{\prime}</annotation></semantics></math>.</p>
</div>
<div id="S3.SS2.p2" class="ltx_para">
<p id="S3.SS2.p2.1" class="ltx_p">Algorithm <a href="#alg5" title="Algorithm 5 ‣ 3.2 Spanning Trees ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref"><span class="ltx_text ltx_ref_tag">5</span></a> provides an overview of our parallel MST implementation which relies on the property that the minimum incident edge, or closest neighbor to each vertex, has to be in the MST (e.g., same as original SLINK). The first step is to identify these edges. Then, edge contraction of the minimum incident edges is applied recursively until a steady state is reached. Instead of explicitly contracting edges through expensive graph coarsening, the MST components are represented using labels (i.e. colors). The problem is reduced to finding the minimum incident edge across color boundaries <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib30" title="" class="ltx_ref">30</a>]</cite>.</p>
</div>
<div id="S3.SS2.p3" class="ltx_para">
<p id="S3.SS2.p3.1" class="ltx_p">Our MST solution is artificially made unique by applying a weight alteration <a href="#S3.SS2.SSS1" title="3.2.1 Weight Alteration ‣ 3.2 Spanning Trees ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 3.2.1</span></a>. MST and MSF are almost identical problems with the difference that MSF refers to the case where <math id="S3.SS2.p3.m1" class="ltx_Math" alttext="G" display="inline" intent=":literal"><semantics><mi>G</mi><annotation encoding="application/x-tex">G</annotation></semantics></math> has multiple strongly connected components. The latter is particularly relevant for <math id="S3.SS2.p3.m2" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN applications which may consist of multiple connected components described in <a href="#S3.SS1" title="3.1 Nearest Neighbors ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 3.1</span></a>. The historical Borůvka MST formula iterates until only one color, or super-vertex, remains. Instead, to find an MSF we detect a steady state and exit if no minimum incident edge to another color has been found.</p>
</div>

<section id="S3.SS2.SSS1" class="ltx_subsubsection">
<h4 class="ltx_title ltx_title_subsubsection"><span class="ltx_tag ltx_tag_subsubsection">3.2.1 </span>Weight Alteration</h4>

<div id="S3.SS2.SSS1.p1" class="ltx_para">
<p id="S3.SS2.SSS1.p1.1" class="ltx_p">Cycle detection and removal was identified as one of the main challenges in previously published GPU solutions <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib30" title="" class="ltx_ref">30</a>]</cite>. The problem can be reduced to selecting an incident edge to every vertex in parallel without creating cycles. Multiple edges of equal minimum weight between two components result in multiple equivalent solutions for the MST problem. In parallel, each component could select a different edge which would result in adding a cycle between them and breaking the tree structure. To address this issue, we propose a simple solution to prevent cycle formation by generating an alteration on the edge weights that guarantees that all weights are different while preserving the relative order of all weights. For any graph that has only a distinct set of edges, this produces a deterministic result. As a result, all vertices can consistently select edges in an embarrassingly parallel fashion. Notice that this has the side effect of altering explicit zeroes, which means our solution cannot support graphs that have zeroed edge weights. The technique for altering the weights is done in 3 steps:</p>
</div>
<div id="S3.SS2.SSS1.p2" class="ltx_para">
<ul id="S3.I1" class="ltx_itemize">
<li id="S3.I1.i1" class="ltx_item" style="list-style-type:none;"><span class="ltx_tag ltx_tag_item">•</span> 
<div id="S3.I1.i1.p1" class="ltx_para">
<p id="S3.I1.i1.p1.1" class="ltx_p">Identify <math id="S3.I1.i1.p1.m1" class="ltx_Math" alttext="\theta&gt;0" display="inline" intent=":literal"><semantics><mrow><mi>θ</mi><mo>&gt;</mo><mn>0</mn></mrow><annotation encoding="application/x-tex">\theta&gt;0</annotation></semantics></math>, where <math id="S3.I1.i1.p1.m2" class="ltx_Math" alttext="\theta" display="inline" intent=":literal"><semantics><mi>θ</mi><annotation encoding="application/x-tex">\theta</annotation></semantics></math> is the minimum edge weight difference between any two pairs of edges in the graph</p>
</div></li>
<li id="S3.I1.i2" class="ltx_item" style="list-style-type:none;"><span class="ltx_tag ltx_tag_item">•</span> 
<div id="S3.I1.i2.p1" class="ltx_para">
<p id="S3.I1.i2.p1.1" class="ltx_p">For each edge in the upper triangular side of the matrix, add noise to each edge weight by generating a random number <math id="S3.I1.i2.p1.m1" class="ltx_Math" alttext="\epsilon\in[0,\theta)" display="inline" intent=":literal"><semantics><mrow><mi>ϵ</mi><mo>∈</mo><mrow><mo stretchy="false">[</mo><mn>0</mn><mo>,</mo><mi>θ</mi><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">\epsilon\in[0,\theta)</annotation></semantics></math>.</p>
</div></li>
<li id="S3.I1.i3" class="ltx_item" style="list-style-type:none;"><span class="ltx_tag ltx_tag_item">•</span> 
<div id="S3.I1.i3.p1" class="ltx_para">
<p id="S3.I1.i3.p1.1" class="ltx_p">Replicate the upper triangular part into the lower triangular part so that <math id="S3.I1.i3.p1.m1" class="ltx_Math" alttext="w_{ij}=w_{ji}" display="inline" intent=":literal"><semantics><mrow><msub><mi>w</mi><mrow><mi>i</mi><mo lspace="0em" rspace="0em">​</mo><mi>j</mi></mrow></msub><mo>=</mo><msub><mi>w</mi><mrow><mi>j</mi><mo lspace="0em" rspace="0em">​</mo><mi>i</mi></mrow></msub></mrow><annotation encoding="application/x-tex">w_{ij}=w_{ji}</annotation></semantics></math>
<br class="ltx_break"></p>
</div></li>
</ul>
</div>
</section>
<section id="S3.SS2.SSS2" class="ltx_subsubsection">
<h4 class="ltx_title ltx_title_subsubsection"><span class="ltx_tag ltx_tag_subsubsection">3.2.2 </span>Minimum incident edges</h4>

<div id="S3.SS2.SSS2.p1" class="ltx_para">
<p id="S3.SS2.SSS2.p1.1" class="ltx_p">A common solution, as noted with <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib12" title="" class="ltx_ref">12</a>]</cite> and <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib9" title="" class="ltx_ref">9</a>]</cite>, is to assign one thread per vertex to scan all edges. However, this comes with the risk that the kernel becomes bound to the slowest performing thread. With the help of <a href="#S3.SS2.SSS1" title="3.2.1 Weight Alteration ‣ 3.2 Spanning Trees ‣ 3 cuSLINK ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref ltx_refmacro_autoref"><span class="ltx_text ltx_ref_tag">§ 3.2.1</span></a>, we overcome the issue of tie-breaking when trying to find the minimum outgoing edge per supervertex as each edge has a unique weight. Thus, overcoming the cycle-detection problem, we divide the task of finding the minimum outgoing edge in two sub-tasks:</p>
<ul id="S3.I2" class="ltx_itemize">
<li id="S3.I2.i1" class="ltx_item" style="list-style-type:none;"><span class="ltx_tag ltx_tag_item">•</span> 
<div id="S3.I2.i1.p1" class="ltx_para">
<p id="S3.I2.i1.p1.1" class="ltx_p"><em id="S3.I2.i1.p1.1.1" class="ltx_emph ltx_font_italic">Minimum Edge Per Vertex</em>: Using the CSR format, we assign 32 threads (one warp) to scan the edges of each vertex. These threads, using shared memory reduction, find an outgoing edge to a destination vertex that is part of a different supervertex than the source and also atomically record a minimum edge weight for that source supervertex</p>
</div></li>
<li id="S3.I2.i2" class="ltx_item" style="list-style-type:none;"><span class="ltx_tag ltx_tag_item">•</span> 
<div id="S3.I2.i2.p1" class="ltx_para">
<p id="S3.I2.i2.p1.1" class="ltx_p"><em id="S3.I2.i2.p1.1.1" class="ltx_emph ltx_font_italic">Minimum Edge Per Supervertex</em> : Continuing from the previous task where we found the minimum outgoing edge for each vertex, we still need to reconcile the minimum source, destination pair for each supervertex. Whichever vertex found an edge that was the minimum for its supervertex adds it to the final solution</p>
</div></li>
</ul>
</div>
<div id="S3.SS2.SSS2.p2" class="ltx_para">

<div id="S3.SS2.SSS3.p1" class="ltx_para">
<p id="S3.SS2.SSS3.p1.1" class="ltx_p">Label propagation in <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib30" title="" class="ltx_ref">30</a>]</cite> is performed by ensuring all vertices explicitly try to converge to supervertex 0, while <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib9" title="" class="ltx_ref">9</a>]</cite> uses graph contraction to form a new graph of supervertices in the current MST iteration. <h3 class="ltx_title ltx_title_subsection"><span class="ltx_tag ltx_tag_subsection">3.3 </span>Dendrogram</h3>

<section id="S3.SS3.SSS1" class="ltx_subsubsection">
<h4 class="ltx_title ltx_title_subsubsection"><span class="ltx_tag ltx_tag_subsubsection">3.3.1 </span>Relabel into Dendrogram</h4>

<div id="S3.SS3.SSS1.p1" class="ltx_para">
<p id="S3.SS3.SSS1.p1.1" class="ltx_p">After computing the minimum spanning tree on the connectivities graph, the resulting <math id="S3.SS3.SSS1.p1.m1" class="ltx_Math" alttext="N-1" display="inline" intent=":literal"><semantics><mrow><mi>N</mi><mo>−</mo><mn>1</mn></mrow><annotation encoding="application/x-tex">N-1</annotation></semantics></math> edges are sorted in parallel by weight. The dendrogram is constructed on the CPU by expanding the total set of vertices from <math id="S3.SS3.SSS1.p1.m2" class="ltx_Math" alttext="N" display="inline" intent=":literal"><semantics><mi>N</mi><annotation encoding="application/x-tex">N</annotation></semantics></math> to <math id="S3.SS3.SSS1.p1.m3" class="ltx_Math" alttext="(N-1)*2" display="inline" intent=":literal"><semantics><mrow><mrow><mo stretchy="false">(</mo><mrow><mi>N</mi><mo>−</mo><mn>1</mn></mrow><mo rspace="0.055em" stretchy="false">)</mo></mrow><mo rspace="0.222em">∗</mo><mn>2</mn></mrow><annotation encoding="application/x-tex">(N-1)*2</annotation></semantics></math> and renumbering the original vertices as they are merged together into the hierarchy. A parent vertex for any level <math id="S3.SS3.SSS1.p1.m4" class="ltx_Math" alttext="i" display="inline" intent=":literal"><semantics><mi>i</mi><annotation encoding="application/x-tex">i</annotation></semantics></math> in the hierarchy, where <math id="S3.SS3.SSS1.p1.m5" class="ltx_Math" alttext="0\leq i&lt;\frac{N-1}{2}" display="inline" intent=":literal"><semantics><mrow><mn>0</mn><mo>≤</mo><mi>i</mi><mo>&lt;</mo><mfrac><mrow><mi>N</mi><mo>−</mo><mn>1</mn></mrow><mn>2</mn></mfrac></mrow><annotation encoding="application/x-tex">0\leq i&lt;\frac{N-1}{2}</annotation></semantics></math>, will always be <math id="S3.SS3.SSS1.p1.m6" class="ltx_Math" alttext="\geq N" display="inline" intent=":literal"><semantics><mrow><mphantom></mphantom><mo>≥</mo><mi>N</mi></mrow><annotation encoding="application/x-tex">\geq N</annotation></semantics></math> and can be computed with the simple formula <math id="S3.SS3.SSS1.p1.m7" class="ltx_Math" alttext="i+N" display="inline" intent=":literal"><semantics><mrow><mi>i</mi><mo>+</mo><mi>N</mi></mrow><annotation encoding="application/x-tex">i+N</annotation></semantics></math>. A union-find structure with union-by-rank and path compression is used to achieve runtime of <math id="S3.SS3.SSS1.p1.m8" class="ltx_Math" alttext="O(N\alpha(N))" display="inline" intent=":literal"><semantics><mrow><mi>O</mi><mo>⁡</mo><mrow><mo stretchy="false">(</mo><mrow><mi>N</mi><mo lspace="0em" rspace="0em">​</mo><mi>α</mi><mo lspace="0em" rspace="0em">​</mo><mrow><mo stretchy="false">(</mo><mi>N</mi><mo stretchy="false">)</mo></mrow></mrow><mo stretchy="false">)</mo></mrow></mrow><annotation encoding="application/x-tex">O(N\alpha(N))</annotation></semantics></math> <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib17" title="" class="ltx_ref">17</a>, <a href="#bib.bib28" title="" class="ltx_ref">28</a>]</cite>.</p>
</div>
<div id="S3.SS3.SSS1.p2" class="ltx_para">
<p id="S3.SS3.SSS1.p2.1" class="ltx_p">The strict ordering of the dendrogram construction step makes it inherently sequential <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib7" title="" class="ltx_ref">7</a>, <a href="#bib.bib20" title="" class="ltx_ref">20</a>]</cite>. More recently, the optimization outlined by <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib17" title="" class="ltx_ref">17</a>]</cite> produces acceptable performance on the CPU, so we exploit as much parallelism in the remaining steps as possible.</p>
</div>
</section>

<section id="S4" class="ltx_section">
<h2 class="ltx_title ltx_title_section"><span class="ltx_tag ltx_tag_section">4 </span>Experiments</h2>

<div id="S4.p1" class="ltx_para">
<p id="S4.p1.1" class="ltx_p">In this section, we benchmark both cuSLINK end-to-end along with our <math id="S4.p1.m1" class="ltx_Math" alttext="k" display="inline" intent=":literal"><semantics><mi>k</mi><annotation encoding="application/x-tex">k</annotation></semantics></math>-NN, <math id="S4.p1.m2" class="ltx_Math" alttext="1" display="inline" intent=":literal"><semantics><mn>1</mn><annotation encoding="application/x-tex">1</annotation></semantics></math>-NN and MST primitives. We show that all components of cuSLINK outperform the available state-of-the-art solutions. All benchmarks are performed w/ CUDA 11.8 on Nvidia A100 GPUs. We selected our comparison implementations based on availability of packages and/or source code which was able to built and run by our best effort. We also made every effort to update existing state-of-the-art solutions to run CUDA 11.8 when needed. Note that we compare against implementations on the CPU only when corresponding GPU source code was not available.</p>
</div>

<h3 class="ltx_title ltx_title_subsection"><span class="ltx_tag ltx_tag_subsection">4.3 </span>Single-linkage Hierarchical Agglomerative Clustering</h3>

<div id="S4.SS3.p1" class="ltx_para">
<p id="S4.SS3.p1.1" class="ltx_p">Since dendrogram construction is not often exposed as an independent step, we evaluate our end-to-end single-linkage hierarchical clustering implementation on the GPU against Scikit-learn’s <span id="S4.SS3.p1.1.1" class="ltx_text ltx_font_italic">AgglomerativeClustering</span> implementation on the CPU in Table <a href="#S4.T4" title="Table 4 ‣ 4.3 Single-linkage Hierarchical Agglomerative Clustering ‣ 4 Experiments ‣ cuSLINK: Single-linkage Agglomerative Clustering on the GPU" class="ltx_ref"><span class="ltx_text ltx_ref_tag">4</span></a>. Each experiment was performed on a NVIDIA DGX1 using several real-world datasets, often encountered in clustering and nearest neighbors research.
These experiments demonstrate that the performance of our SLHC implementation has the potential to lower the time spent in compute during the data analysis process, enabling near real-time speeds for data sets that take nearly 40 minutes to process on the CPU.</p>

<section id="S5" class="ltx_section">
<h2 class="ltx_title ltx_title_section"><span class="ltx_tag ltx_tag_section">5 </span>Conclusion</h2>

<div id="S5.p1" class="ltx_para">
<p id="S5.p1.1" class="ltx_p">In addition to a novel, modular, and state-of-the-art implementation of single-linkage hierarchical clustering, we’ve outlined and contributed multiple reusable, novel and state-of-the-art primitives in this paper.
These primitives include k-nearest graph construction, graph-based minimum spanning tree solver, and a novel parallel dendrogram cluster extraction method.</p>
</div>
<div id="S5.p2" class="ltx_para">
<p id="S5.p2.1" class="ltx_p">We demonstrated that our primitives are both flexible and fast, and have a potential to impact several different industries as existing state-of-the-art methods for end-to-end single-linkage clustering are intractable on large datasets. These primitives are all fully open source and available as part of the RAFT library (https://github.com/rapidsai/raft).</p>
</div>
</section>

<section id="Pt0.A2" class="ltx_appendix">
<h2 class="ltx_title ltx_title_appendix"><span class="ltx_tag ltx_tag_appendix">Appendix Appendix B </span>GPU Architecture</h2>

<div id="Pt0.A2.p1" class="ltx_para">
<p id="Pt0.A2.p1.1" class="ltx_p">The largest GPUs today contain thousands of hardware processing cores that are divided into groups of 32 or 64, which can execute instructions concurrently. The instructions for each group of cores are orchestrated by a streaming multiprocessor (SM). From a programming perspective, these groups are called warps and each physical core executing an instruction is known as a thread. Each warp can process a single instruction at a time across its threads in parallel using a paradigm called single-instruction multiple data (SIMD).</p>
</div>
<div id="Pt0.A2.p2" class="ltx_para">
<p id="Pt0.A2.p2.1" class="ltx_p">It’s important that threads within a warp minimize conditional branching that will cause the threads to wait for each branch to complete before proceeding. This is called thread divergence, and can severely limit effective parallel execution. On the Volta and Ampere architectures, each SM can track the progress of up to 64 warps concurrently <cite class="ltx_cite ltx_citemacro_cite">[<a href="#bib.bib29" title="" class="ltx_ref">29</a>]</cite>, and rapidly switch between them to fully utilize the SM. Each SM has a set of registers available which allows warps to perform collective operations, such as reductions. Warps can be grouped into blocks and a small amount of memory can be shared across the threads and warps.</p>
</div>
<div id="Pt0.A2.p3" class="ltx_para">
<p id="Pt0.A2.p3.1" class="ltx_p">Global, or device, memory can be accessed by all of the SMs in the GPU. Accesses to contiguous device memory locations within a warp can be coalesced into a single blocked transaction so long as the accesses are performed in the same operation. In SIMD architectures, uniform patterns can be critical to performance unless latencies from non-uniform processing, such as uncoalesced memory accesses, can be hidden with increased parallelism.</p>
</div>
<div id="Pt0.A2.p4" class="ltx_para">
<p id="Pt0.A2.p4.1" class="ltx_p">Registers provide the fastest storage, and it’s generally preferable to perform reductions and arithmetic as intra-warp collective operations where possible. Intra-block shared memory is also generally preferred over global memory when a problem can be made small enough to benefit.</p>
</div>
</section>
